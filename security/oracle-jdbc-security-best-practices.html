Security Best Practices with the Oracle JDBC driver

Protect database access with password-less connections, safe SQL, encrypted transport, and least-privilege controls.

Key Takeaways

  • Use short-lived OCI IAM or Entra tokens, or retrieve database passwords through a vault provider.
  • Bind SQL values, allowlist dynamic identifiers, and keep TLS server identity validation enabled.
  • Centralize connection configuration while keeping database, configuration-store, and vault permissions separate.
  • Manage timeouts, pooled connections, and dependency updates as part of the security boundary.

The Oracle JDBC driver sits at an important security boundary: it carries database credentials, sends application input to SQL, and often runs inside a cloud workload with access to valuable data. A strong design combines identity-based authentication, encrypted transport, parameterized SQL, least privilege, and careful handling of driver resources.

This article uses the JDBC Thin driver. Every database address below uses Easy Connect Plus, including addresses loaded from centralized configuration, for example:

String url = "jdbc:oracle:thin:@tcps://db.example.com:1522/appdb?connect_timeout=10";

Easy Connect Plus makes the host, port, and service explicit without a naming file and can carry connection properties after ?. The examples keep provider configuration in a Properties object instead of putting secrets or tokens in the URL. This reduces the chance that a URL copied into a log, metric, or exception will expose sensitive data.

1. Password-less connection

Choose between two distinct patterns. Token authentication removes the database password from the connection flow. A vault password provider removes the password from application source and configuration, but the database still authenticates with a password. Neither approach removes the need to protect the cloud identity used to acquire the credential.

For the vault and token provider examples below, add the Oracle JDBC provider extension that matches the cloud:

<dependency>
  <groupId>com.oracle.database.jdbc</groupId>
  <artifactId>ojdbc11</artifactId>
  <version>${ojdbc.version}</version>
</dependency>

<!-- Use a version compatible with the ojdbc driver in the application. -->
<dependency>
  <groupId>com.oracle.database.jdbc</groupId>
  <artifactId>ojdbc-provider-oci</artifactId>
  <version>${ojdbc.providers.version}</version>
</dependency>

<!-- Add this instead of, or in addition to, the OCI provider when needed. -->
<dependency>
  <groupId>com.oracle.database.jdbc</groupId>
  <artifactId>ojdbc-provider-azure</artifactId>
  <version>${ojdbc.providers.version}</version>
</dependency>

The provider artifacts implement Oracle JDBC service-provider interfaces. The companion token examples use JDBC 23.26.3.0.0 and OCI/Azure providers 1.1.0; the complete class below requires Java 17 or later. Pin each extension to a version tested with the application’s driver and runtime; do not silently float a security-sensitive dependency.

OCI IAM: instance and resource principals

Use the compute instance's identity with OCI_INSTANCE_PRINCIPAL, or a supported managed workload's identity with OCI_RESOURCE_PRINCIPAL. Map the appropriate IAM dynamic group into the database and grant the workload a database-scoped policy. An instance/resource principal is not an IAM user; do not use an exclusive IAM-user mapping for it.

The following complete class uses the simplified token-authentication property. With the matching provider JAR on the classpath, the driver selects it automatically; explicit oracle.jdbc.provider.accessToken settings are unnecessary. The provider acquires and caches the database token and its proof-of-possession key. No database username or password is supplied.

import java.sql.*;
import java.util.Properties;

public class WhoAmI {
  public static void main(String[] args) throws SQLException {
    String url = "jdbc:oracle:thin:@tcps://db.example.com:1522/appdb";
    Properties p = new Properties();
    p.setProperty("oracle.jdbc.tokenAuthentication", "OCI_INSTANCE_PRINCIPAL");
    p.setProperty("oracle.jdbc.ociCompartment", "ocid1.compartment.oc1..example");
    p.setProperty("oracle.jdbc.ociDatabase", "ocid1.autonomousdatabase.oc1..example");
    try (Connection c = DriverManager.getConnection(url, p);
         PreparedStatement s = c.prepareStatement("""
           SELECT SYS_CONTEXT('USERENV','SESSION_USER') AS database_user,
                  SYS_CONTEXT('USERENV','AUTHENTICATED_IDENTITY') AS external_identity,
                  SYS_CONTEXT('USERENV','AUTHENTICATION_METHOD') AS authentication_method,
                  SYS_CONTEXT('USERENV','IDENTIFICATION_TYPE') AS identification_type,
                  SYS_CONTEXT('USERENV','OS_USER') AS os_user
           FROM sys.dual
           """);
         ResultSet rows = s.executeQuery()) {
      ResultSetMetaData meta = rows.getMetaData();
      while (rows.next()) {
        for (int i = 1; i <= meta.getColumnCount(); i++) {
          System.out.println(meta.getColumnName(i) + " : " + rows.getString(i));
        }
      }
    }
  }
}

For a resource principal, change only the selection to OCI_RESOURCE_PRINCIPAL and run in the corresponding identity-enabled workload. Other provider choices include OCI_API_KEY, OCI_DELEGATION_TOKEN, and OCI_INTERACTIVE. Scope access to one database where possible, protect diagnostic identity output, and test token refresh with new physical connections. Never put a live token in a URL.

Microsoft Entra ID: managed identity and service principals

Entra uses a bearer JWT rather than the OCI token/PoP-key pair. The database must trust the Entra resource application, and the workload must have its database app role mapped to a database schema. Prefer managed identity on supported Azure hosts; enabling an identity alone does not assign its database role.

Properties p = new Properties();
p.setProperty("oracle.jdbc.tokenAuthentication", "AZURE_MANAGED_IDENTITY");
p.setProperty("oracle.jdbc.azureDatabaseApplicationIdUri",
    "https://example.onmicrosoft.com/<database-application-id>");
try (Connection c = DriverManager.getConnection(
    "jdbc:oracle:thin:@tcps://db.example.com:1522/appdb", p)) {
  // No database password or manually acquired token is passed.
}

Use the registered database resource URI, without a scope suffix. Select a user-assigned managed identity with its client ID; clear unrelated client-ID settings for a system-assigned identity. For a service principal, use AZURE_SERVICE_PRINCIPAL with an externally supplied client certificate or client secret. Human workflows can use AZURE_INTERACTIVE or AZURE_DEVICE_CODE with public-client registration, delegated permission, user role assignment, and tenant consent.

See the OCI IAM and Entra JDBC token walkthrough for file, SDK, provider and UCP alternatives, and the JDBC token-authentication property reference for the exact supported properties.

Authentication is not end-user data authorization

A token establishes an authenticated database identity; it does not by itself implement end-user row, column, or cell policies. Oracle AI Database Deep Data Security can enforce fine-grained data access in the database. Keep the workload's database-login token distinct from any end-user identity carried for DDS authorization. See Develop Database-Enforced End-User Auth with Oracle AI Database Deep Data Security and Java.

OCI Vault password

Store the password as an OCI Vault secret and grant the workload identity permission to read that specific secret. The OCI resource provider then supplies the password to the driver when the connection is opened:

import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;
import java.util.Properties;

String url = "jdbc:oracle:thin:@tcps://db.example.com:1522/appdb";

Properties properties = new Properties();
properties.setProperty("user", "APP_USER");
properties.setProperty(
    "oracle.jdbc.provider.password",
    "ojdbc-provider-oci-vault-password");
properties.setProperty(
    "oracle.jdbc.provider.password.ocid",
    "ocid1.vaultsecret.oc1..example");
properties.setProperty(
    "oracle.jdbc.provider.password.authenticationMethod",
    "instance-principal");

try (Connection connection = DriverManager.getConnection(url, properties)) {
  // The provider supplies the password; application code does not handle it.
}

Use resource-principal instead of instance-principal when the application runs as an OCI resource principal, for example in a serverless or managed workload. The identity still needs a narrowly scoped policy to read the secret.

Azure Key Vault password

The equivalent Azure provider reads a Key Vault secret. Managed identity avoids placing a client secret in the application:

String url = "jdbc:oracle:thin:@tcps://db.example.com:1522/appdb";

Properties properties = new Properties();
properties.setProperty("user", "APP_USER");
properties.setProperty(
    "oracle.jdbc.provider.password",
    "ojdbc-provider-azure-key-vault-password");
properties.setProperty(
    "oracle.jdbc.provider.password.vaultUrl",
    "https://app-secrets.vault.azure.net/");
properties.setProperty(
    "oracle.jdbc.provider.password.secretName",
    "oracle-app-password");
properties.setProperty(
    "oracle.jdbc.provider.password.authenticationMethod",
    "managed-identity");

try (Connection connection = DriverManager.getConnection(url, properties)) {
  // Use the connection; do not log the resolved password.
}

If a service principal is required, prefer certificate-based authentication and keep the certificate private key outside the application image. In either cloud, use secret versioning and rotation, test rotation before changing the active version, and grant the workload only the get/read permission it needs.

Password providers across clouds

Set oracle.jdbc.provider.password to the provider name and put its parameters under oracle.jdbc.provider.password.. Add the corresponding com.oracle.database.jdbc:ojdbc-provider-* artifact. The following table documents the password resource providers, not token providers:

Secret store / extensionPassword providerSecret-selection parameters
OCI Vault / ociojdbc-provider-oci-vault-passwordocid; choose an explicit workload authentication method.
Azure Key Vault / azureojdbc-provider-azure-key-vault-passwordvaultUrl, secretName; managed identity or an approved service principal.
GCP Secret Manager / gcpojdbc-provider-gcp-secretmanager-passwordsecretVersionName, e.g. projects/PROJECT/secrets/SECRET/versions/VERSION.
AWS Secrets Manager / awsojdbc-provider-aws-secrets-manager-passwordsecretName; fieldName selects a field when the secret is a JSON object.

Use GCP workload credentials/Application Default Credentials, an AWS workload role, or the documented Vault authentication mechanism appropriate to the runtime. These credentials authorize secret retrieval, not SQL operations. Protect bootstrap credentials, pin supported extension versions, restrict secret reads, and test rotation and cache behavior. The Java process necessarily receives the resolved password; a provider is not protection against a compromised process.

Build a custom password provider when needed

Implement oracle.jdbc.spi.PasswordProvider, including its name, parameters and password retrieval, and register the implementation through Java's service-provider mechanism (META-INF/services/oracle.jdbc.spi.PasswordProvider, or a module provides declaration). Package it on the runtime classpath and select its name with oracle.jdbc.provider.password. Return the secret as the required character array; avoid logging, unnecessary copies or indefinite caching. Add bounded retries, rotation tests and least-privilege authentication to the backing store.

2. Centralized configuration: a higher-level abstraction

A configuration provider supplies the connection settings as a group: database address, JDBC properties and references to secrets or wallets. It sits above individual password/token providers. Administrators can manage the configuration independently of application code; protect its integrity because changing it can redirect connections or change authentication.

JSON in object storage, a filesystem, or an HTTPS service

Store JSON in OCI Object Storage, Amazon S3, Google Cloud Storage, or Azure Blob Storage, or distribute it as a protected local file or HTTPS resource. The retrieval mechanism must support that store's authentication; a private object is not automatically readable by the generic HTTPS provider.

OCI Object Storageconfig-ociobject provider with the object's HTTPS location and OCI authentication.
Amazon S3jdbc:oracle:thin:@config-awss3://s3://BUCKET/database.json?key=prod
Google Cloud Storagejdbc:oracle:thin:@config-gcpstorage://gs://BUCKET/database.json?key=prod

The config-* URL locates configuration, not the database. Inside JSON, the required key is named connect_descriptor, but its value can be an EZConnect+ address; no naming alias or full Oracle Net descriptor is necessary. For example:

{
  "prod": {
    "connect_descriptor": "tcps://db.example.com:1522/appdb",
    "jdbc": {
      "oracle.jdbc.tokenAuthentication": "AZURE_MANAGED_IDENTITY",
      "oracle.jdbc.azureDatabaseApplicationIdUri":
        "https://example.onmicrosoft.com/<database-application-id>",
      "oracle.jdbc.ReadTimeout": "30000"
    }
  }
}

This is compatible with passwordless authentication: omit database user and password for the token flow, and retain the required token-provider extension on the classpath. Replace the Entra properties with the OCI token properties for an OCI workload. Configuration-store authentication, token acquisition and database authorization are separate boundaries. For password authentication, use a vault reference rather than embedding a secret in the JSON. File and HTTPS configuration support is built into the driver; cloud-specific retrieval and secret references require their corresponding extensions. See the configuration-provider API.

Azure App Configuration with an Azure Key Vault secret

The Azure extension can also load settings from Azure App Configuration. Use a key prefix and label to select the application's environment:

String configUrl =
    "jdbc:oracle:thin:@config-azure://myappconfig?key=/sales_app1/&label=prod";
try (Connection c = DriverManager.getConnection(configUrl)) {
  // The Azure provider resolves the configuration and Key Vault reference.
}

Create /sales_app1/connect_descriptor with value tcps://db.example.com:1522/appdb, /sales_app1/user with the application schema, and /sales_app1/password as an App Configuration Key Vault reference to the database-password secret. Create the reference through the portal or SDK so its Key Vault reference content type is correct; do not store a plain JSON string as a normal text value. Put driver properties under /sales_app1/jdbc/. Use label prod consistently.

Give the workload read access to App Configuration and separate permission to read the referenced Key Vault secret. Use managed identity when available. This particular example still uses a database password, resolved at runtime; for token authentication, omit the user/password entries and supply the token properties under the JDBC prefix instead. See the Azure configuration and resource-provider documentation.

3. Prevent SQL injection

Bind values with PreparedStatement

A regular Statement executing dynamic SQL built from request strings lets input change SQL syntax. Never concatenate request data into SQL; use PreparedStatement and bind the values instead. A bind variable keeps data separate from the SQL grammar, and it also lets the driver and database reuse parsed statements:

String url = "jdbc:oracle:thin:@tcps://db.example.com:1522/appdb";

// Reuse the password-provider configuration from the OCI/Azure example.
Properties properties = passwordProviderProperties;

String sql = "select order_id, total "
    + "from orders "
    + "where customer_id = ? and status = ?";

try (Connection connection = DriverManager.getConnection(url, properties);
     PreparedStatement statement = connection.prepareStatement(sql)) {
  statement.setLong(1, customerId);
  statement.setString(2, status);

  try (ResultSet results = statement.executeQuery()) {
    while (results.next()) {
      // Process the row.
    }
  }
}

The same rule applies to INSERT, UPDATE, DELETE, PL/SQL calls, dates, numbers, JSON, and LIKE patterns. If a value is optional, add a known SQL fragment in application code and continue to bind the value; do not build a fragment by concatenating the raw request.

Treat identifiers separately

JDBC bind variables represent values, not table names, column names, sort directions, or SQL keywords. For dynamic identifiers:

  1. Prefer a fixed mapping or allowlist.
  2. Reject anything outside that allowlist.
  3. Use Statement.enquoteIdentifier to produce a valid identifier, quoted where required.
  4. Continue using bind variables for every parameter value in the statement.
import java.sql.Statement;
import java.util.Locale;
import java.util.Set;

private static final Set<String> ALLOWED_TABLES =
    Set.of("ORDERS", "ORDERS_ARCHIVE");

static String safeTableName(Connection connection, String requested)
    throws SQLException {
  String canonical = requested.toUpperCase(Locale.ROOT);
  if (!ALLOWED_TABLES.contains(canonical)) {
    throw new IllegalArgumentException("Unsupported table");
  }

  try (Statement statement = connection.createStatement()) {
    return statement.enquoteIdentifier(canonical, false);
  }
}

String url = "jdbc:oracle:thin:@tcps://db.example.com:1522/appdb";
// Reuse the password-provider configuration from the OCI/Azure example.
Properties properties = passwordProviderProperties;

try (Connection connection = DriverManager.getConnection(url, properties)) {
  String table = safeTableName(connection, requestedTable);
  String sql = "select order_id, total from " + table
      + " where customer_id = ?";

  try (PreparedStatement statement = connection.prepareStatement(sql)) {
    statement.setLong(1, customerId);
    try (ResultSet results = statement.executeQuery()) {
      // Process the row.
    }
  }
}

enquoteIdentifier protects the SQL syntax of the identifier, but it does not decide whether the caller should be allowed to access that table. The allowlist remains essential. Do not use enquoteLiteral as a substitute for a PreparedStatement; bind values instead.

4. Encrypt the connection and validate the server

Use TCPS in the Easy Connect Plus URL for connections that cross a host or network boundary. Keep server certificate and distinguished-name validation enabled (it's the default):

String url = "jdbc:oracle:thin:@tcps://db.example.com:1522/appdb"
    + "?connect_timeout=10";

Do not disable certificate validation to work around a wallet or hostname problem. Fix the trust configuration, and explicitly configure the expected server DN when the deployment requires it. For Autonomous Database mTLS, store the wallet in a managed secret store and use the cloud provider’s wallet provider rather than committing a wallet to the repository or container image.

5. Apply least privilege at the database boundary

Create a dedicated database account or schema for each application or trust boundary. Grant only the tables, views, packages, and operations that application needs. In particular:

  • Never run application traffic as SYS, SYSTEM, or another administrative account.
  • Prefer views and stored procedures when they provide a smaller, clearer data boundary.
  • Separate read-only and read/write identities.
  • Restrict database-network access with private endpoints, firewalls, security lists, and security groups.
  • Treat a vault read permission and a database grant as separate controls; an application should not receive either one broadly.

6. Protect credentials, tokens, and diagnostics

  • Do not log JDBC URLs, Properties, connection strings, access tokens, secret values, or complete SQL statements containing sensitive data.
  • Redact SQLException details before returning them to a caller. Keep detailed diagnostics in access-controlled logs.
  • Do not put oracle.jdbc.accessToken, passwords, or wallet material in an Easy Connect Plus query string.
  • Use short-lived tokens and rotate vault secrets. Revoke and replace credentials when a workload, image, or identity is decommissioned.
  • Lock down configuration files with operating-system permissions when a file-based provider is unavoidable.
  • Disable verbose driver tracing in production unless it is needed for a controlled incident, and verify that the logging pipeline redacts connection properties.

7. Bound work and clean up resources

Use try-with-resources for Connection, PreparedStatement, Statement, and ResultSet. Set application-appropriate query and network timeouts so a stalled database or network path cannot consume every request thread. Use a maintained connection pool for production workloads, configure a maximum connection lifetime, validate connections when they are borrowed, and reset session state before returning them to the pool.

Keep transactions short, commit deliberately, and roll back on failure. Never share a JDBC Connection or mutable statement object across request threads. These practices limit the impact of abandoned sessions, reduce resource-exhaustion risks, and prevent one request’s session state from leaking into another.

8. Keep the dependency and runtime chain current

Use a supported JDK and a current Oracle JDBC driver/provider combination. Review driver and provider release notes, scan the dependency graph, verify artifacts in the build pipeline, and remove unused JDBC extensions. A secure database connection is only as strong as the application, provider library, cloud identity, TLS trust configuration, and database grants that surround it.

Practical review checklist

Before shipping a JDBC integration, verify that:

  • The URL is Easy Connect Plus and uses tcps for remote traffic.
  • The application has no database password, token, wallet, or secret value in source control.
  • Vault access uses a workload identity with the smallest possible read permission.
  • Token authentication uses an explicit, narrow scope and a database/IAM mapping.
  • Centralized configuration uses EZConnect+, contains no plaintext secrets, and has controlled write access.
  • All request-controlled values use PreparedStatement bind variables.
  • Dynamic identifiers are allowlisted and passed through enquoteIdentifier.
  • TLS server identity validation remains enabled.
  • Database privileges, network access, logs, pool settings, and timeouts have been reviewed together.

FAQ

Does retrieving a password from a vault eliminate database passwords?

No. A vault provider keeps the password out of the application’s source and configuration, but the database still uses password authentication. A short-lived identity token removes the database password from that application flow.

Can bind variables protect dynamic table and column names?

Bind variables protect values, not SQL identifiers. Use a fixed mapping or allowlist for identifiers, quote them with Statement.enquoteIdentifier, and continue binding every parameter value.

Should certificate validation be disabled when a connection fails?

No. Fix the trust, wallet, or hostname configuration. Keep server certificate and distinguished-name validation enabled, and configure the expected server DN when required.

What else belongs in a JDBC security review?

Review database grants, network access, configuration-store integrity, vault permissions, logging, token and secret rotation, pool settings, timeouts, and supported driver/provider and JDK versions together.
