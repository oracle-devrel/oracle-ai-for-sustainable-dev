Passwordless Java Connections to Oracle AI Database with OCI IAM and Microsoft Entra ID

Use JDBC token authentication directly, or let the 23c JDBC provider extensions obtain and refresh OCI IAM or Microsoft Entra ID access tokens for you.

By Paul Parkinson · September 2026 · Technical references checked September 28, 2026

Key Takeaways

  • Oracle JDBC can authenticate to Autonomous AI Database with short-lived OCI IAM or Microsoft Entra ID tokens instead of a database password.
  • The file-based OCI_TOKEN flow remains useful for tokens produced by the OCI CLI, while 23c JDBC provider extensions can acquire tokens through OCI and Azure SDK credentials.
  • OCI IAM uses a token plus a proof-of-possession private key; an Entra token uses the database application audience and a configured Azure credential.
  • Token authentication does not replace TLS, database-side identity mapping, least-privilege policies, or pool lifecycle testing.

Yes. A Java application can connect to Oracle AI Database without putting a database password in its JDBC call. With OCI IAM, the application can use an OCI database token and its proof-of-possession key. With Microsoft Entra ID, it can use an access token issued for the database application. In both cases, Oracle JDBC sends the token during authentication and the database validates it against its configured identity provider and user mapping.

The current implementation choice is between two layers. The JDBC driver can read a token from a file or accept a token value supplied by the application. Starting with the 23c driver, service-provider extensions can obtain tokens through the OCI or Azure SDK and expose them to JDBC, so an existing OracleDataSource-based application may only need dependency and connection-property changes. The provider modules also cache tokens and refresh them before expiry.

What Changed Since the Original IAM Token Example?

The original Oracle Developers walkthrough showed how to generate an IAM database token with the OCI CLI or SDK, point JDBC at the token directory, and refresh the token for a connection pool. That pattern is still valid, but the current JDBC line adds more choices:

ApproachToken acquisitionBest fit
File-based OCI_TOKENOCI CLI or application code writes token and oci_db_key.pem to a directory.Simple automation, existing OCI CLI workflows, and applications that already manage a token refresh job.
JDBC provider for OCIojdbc-provider-oci uses OCI SDK credentials such as an API-key config file, instance principal, resource principal, Cloud Shell, or interactive login.OCI-hosted workloads and Java applications that should not implement token acquisition code.
JDBC provider for Azureojdbc-provider-azure uses Azure SDK credentials such as a service principal, certificate, managed identity, device code, or interactive login.Azure-hosted workloads, Entra service principals, and interactive Java clients.

The provider route does not remove configuration work: the database must trust the identity provider, the principal must be mapped to a database user, the token scope must identify the database resource, and the application must include compatible JDBC and provider artifacts.

Prerequisites and Database Configuration

Complete the identity-provider setup before debugging Java code. The exact SQL and console steps vary by Autonomous AI Database service and identity provider, so use the current Autonomous AI Database IAM authentication guide and the JDBC client-side security guide as the authoritative setup references.

  1. Enable external token authentication. Configure the Autonomous AI Database identity provider for OCI IAM or Microsoft Entra ID.
  2. Create the database mapping. Map the IAM user/group or Entra application/service principal to the database user that should own the session. The mapping is database authorization; access to the OCI or Azure resource alone is not enough.
  3. Grant only the required cloud permission. For OCI, scope the IAM policy to the required Autonomous Database resource. For Entra ID, expose or use the database application scope and grant the application the appropriate permission.
  4. Use a secure database connect descriptor. Use a TCPS connection string and the required ADB wallet or TLS configuration. Token authentication authenticates the database session; it does not replace network encryption or server identity validation.
  5. Choose the token flow. Use the file-based flow when an external process already owns token generation, or use a provider extension when the Java process should obtain and refresh the token.

Option 1: Connect with an OCI IAM Token from the File System

The OCI CLI can generate the database token and proof-of-possession key:

oci iam db-token get --profile DEFAULT

# Default output directory:
# $HOME/.oci/db-token/token
# $HOME/.oci/db-token/oci_db_key.pem

The database token is short-lived. The JDBC reference documents the default location as $HOME/.oci/db-token/; a custom directory can be supplied with oracle.jdbc.tokenLocation. For OCI_TOKEN, the directory must contain both the JWT file named token and the PKCS#8 RSA private key named oci_db_key.pem.

import java.sql.Connection;
import java.sql.SQLException;
import java.util.Properties;
import oracle.jdbc.OracleConnection;
import oracle.jdbc.datasource.impl.OracleDataSource;

OracleDataSource dataSource = new OracleDataSource();
dataSource.setURL(System.getenv("ADB_JDBC_URL")); // Use a TCPS URL or wallet-backed descriptor.

Properties properties = new Properties();
properties.setProperty(
    OracleConnection.CONNECTION_PROPERTY_TOKEN_AUTHENTICATION,
    "OCI_TOKEN");
String tokenDirectory = System.getenv("OCI_DB_TOKEN_DIR");
if (tokenDirectory != null && !tokenDirectory.isBlank()) {
    properties.setProperty(
        OracleConnection.CONNECTION_PROPERTY_TOKEN_LOCATION,
        tokenDirectory);
}
dataSource.setConnectionProperties(properties);

try (Connection connection = dataSource.getConnection()) {
    // Run application SQL with a token-authenticated database session.
}

When the token directory is the default location, omit the custom token-location property. Do not set a username or password alongside token authentication. A background refresh process should replace the token and key atomically and before the next physical connection is created. For an application-managed token, use a thread-safe supplier and the JDBC token cache rather than sharing an expired token across a pool.

Option 2: Let the OCI JDBC Provider Obtain the Token

The OCI JDBC provider exposes an access-token resource provider named ojdbc-provider-oci-token. It supports OCI SDK authentication methods including an OCI configuration file, instance principal, resource principal, Cloud Shell, and interactive authentication. The provider accepts a least-privilege database scope such as a compartment-and-database URN and refreshes the cached JWT before it expires.

Add the provider alongside the Oracle JDBC driver. The versions below are a concrete example; pin a compatible driver/provider pair for your application and verify the current release in Maven Central.

<properties>
  <oracle.jdbc.version>23.26.2.0.0</oracle.jdbc.version>
  <ojdbc.extensions.version>1.1.0</ojdbc.extensions.version>
</properties>

<dependency>
  <groupId>com.oracle.database.jdbc</groupId>
  <artifactId>ojdbc17-production</artifactId>
  <version>${oracle.jdbc.version}</version>
  <type>pom</type>
</dependency>
<dependency>
  <groupId>com.oracle.database.jdbc</groupId>
  <artifactId>ojdbc-provider-oci</artifactId>
  <version>${ojdbc.extensions.version}</version>
</dependency>

Configure the provider in the same Properties object used by the data source:

Properties properties = new Properties();
properties.setProperty(
    "oracle.jdbc.provider.accessToken",
    "ojdbc-provider-oci-token");
properties.setProperty(
    "oracle.jdbc.provider.accessToken.authenticationMethod",
    "config-file");
properties.setProperty(
    "oracle.jdbc.provider.accessToken.configFile",
    "/opt/app/.oci/config");
properties.setProperty(
    "oracle.jdbc.provider.accessToken.profile",
    "DEFAULT");
properties.setProperty(
    "oracle.jdbc.provider.accessToken.scope",
    "urn:oracle:db::id::<compartment-ocid>::<database-ocid>");

OracleDataSource dataSource = new OracleDataSource();
dataSource.setURL(System.getenv("ADB_JDBC_URL"));
dataSource.setConnectionProperties(properties);

try (Connection connection = dataSource.getConnection()) {
    // The provider supplies the OCI IAM access token when JDBC opens the session.
}

For an OCI compute workload, change authenticationMethod to instance-principal or resource-principal when the runtime actually provides that identity. The provider's scope should be as narrow as possible: a single database is less privileged than a compartment, and a compartment is less privileged than the tenancy-wide wildcard.

Option 3: Let the Azure JDBC Provider Obtain an Entra ID Token

The Azure JDBC provider exposes ojdbc-provider-azure-token. Its scope is the application ID URI of the database resource followed by a named scope or /.default. The provider uses Azure SDK credentials and can cache the token, refreshing it before expiration.

For an application service principal, configure the provider with environment variables or a secret/certificate manager. Prefer a certificate or workload identity where that is supported by your deployment instead of embedding a client secret in source code.

export AZURE_TENANT_ID=<tenant-id>
export AZURE_CLIENT_ID=<database-application-client-id>
export AZURE_CLIENT_SECRET=<service-principal-secret> # Prefer a certificate or federated credential when available.
Properties properties = new Properties();
properties.setProperty(
    "oracle.jdbc.provider.accessToken",
    "ojdbc-provider-azure-token");
properties.setProperty(
    "oracle.jdbc.provider.accessToken.authenticationMethod",
    "service-principal");
properties.setProperty(
    "oracle.jdbc.provider.accessToken.scope",
    "https://example.com/<database-application-id>/.default");

OracleDataSource dataSource = new OracleDataSource();
dataSource.setURL(System.getenv("ADB_JDBC_URL"));
dataSource.setConnectionProperties(properties);

try (Connection connection = dataSource.getConnection()) {
    // Azure SDK credentials are used to request the database access token.
}

For an Azure-hosted workload, use managed-identity and set a user-assigned client ID when necessary. For a human-operated desktop application, interactive or device-code can be appropriate. The provider also supports certificate-backed service principals. The database application ID URI and requested scope must match the resource configured in Microsoft Entra ID and in the database.

The direct JDBC modes are useful when you want the driver itself to call the identity SDK. The extension providers are useful when you want a stable provider property and cloud-specific dependencies outside the application’s token-acquisition code. Do not mix a provider-managed token with a database username/password on the same data source unless the driver documentation explicitly supports that combination.

Connection Pools Need a Token Lifecycle

A token is not a permanent replacement for a password. It is an expiring credential used when a physical database session is created. This matters for UCP, application servers, and any pool that keeps connections alive:

  1. Refresh before expiry. The provider extensions cache JWTs and refresh them before expiration. A file-based implementation must refresh the files itself.
  2. Test new physical connections. An expired token may not affect an already established session, but it will fail when the pool needs to create or replace a physical connection.
  3. Keep pool identity stable. Do not allow a connection created for one application identity or database target to be reused for another identity without a documented pool boundary.
  4. Handle revocation separately. Token expiry, IAM policy changes, Entra role changes, and an already-open database session have different timing. Define how quickly each must take effect.
  5. Redact sensitive values. Never log token bodies, proof-of-possession keys, client secrets, or credential-bearing JDBC URLs.

For a simple application, the provider access-token property can be attached to an OracleDataSource or UCP connection factory. For a custom token service, use a thread-safe AccessToken supplier and its cache. In either design, use a TCPS URL and keep database authorization in the database rather than assuming a valid cloud token grants unrestricted SQL access.

Summary

The 2022 IAM-token pattern still provides a clear, portable baseline: generate a short-lived token, give JDBC the token directory, and refresh it before creating new pooled connections. The 23c JDBC provider extensions make the same design easier to operate by moving cloud-specific token acquisition into supported OCI and Azure provider modules. The right choice depends on where the Java process runs and which identity it is allowed to use.

Whichever path you select, keep the security boundary explicit: the cloud identity obtains a database-scoped token, Oracle AI Database maps that identity to a database principal, the JDBC driver protects the network connection, and database grants determine what that principal can do.

Frequently Asked Questions

Does token authentication make the application completely secretless?

Not automatically. It can remove the database password, but an application may still use an OCI API key, Azure client secret, certificate, wallet, or workload identity. Inventory and protect every credential in the chain.

What is the difference between OCI_TOKEN and OAUTH?

OCI_TOKEN is the OCI IAM database-token flow and requires both the token and its proof-of-possession private key. OAUTH is the generic bearer-token mode and reads only the token. Use the mode that matches the token issued by the identity provider.

Can I use a provider extension without changing repository or SQL code?

Usually, yes. If the application already uses an Oracle DataSource, adding the provider dependency and connection properties can keep SQL and repository code unchanged. You still need the database identity mapping, cloud permissions, TLS configuration, and pool lifecycle tests.

Can a valid OCI IAM or Entra token access every table?

No. A token authenticates an identity; database users, grants, roles, and policies authorize SQL. Keep those grants least-privileged and test both permitted and denied operations.
